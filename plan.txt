  What the links changed

  - CyberGym. 1,507 tasks from ARVO and OSS-Fuzz. The agent gets a vulnerable
    repo plus a vulnerability description and has to write a PoC input. It
    submits the PoC to a CyberGym server, which runs it against the prebuilt

    - Server mode. Full mode needs about 10 TB because it can recompile.
      Binary-only mode needs about 130 GB and checks PoCs against the prebuilt
      binaries, so that's the mode to use.
    - Difficulty level. Run at level1 (description + repo), the main setting in
      the paper.
  - SEC-bench Pro is a patching benchmark, not PoC generation. It has 183
    JavaScript-engine bugs: 103 V8 and 80 SpiderMonkey. Each instance has its
    own Docker image of about 9 GB (I checked on Docker Hub), so about 1.65 TB
    for all 183. Grading means applying the model's patch, rebuilding d8 or js
    incrementally, and checking that the bug no longer triggers. These are long
    tasks with heavy CPU use.
  - Gaps:
    - The public SEC-bench repo doesn't mention the Pro version.
    - The dataset has no PoC field. It probably lives inside each image, but we
      need to confirm.
    - Neither harness documents vLLM or OpenAI-compatible endpoints.
    - Neither benchmark exists in our Gym checkout.

  Key design choice: run 3 models at once per node, task by task

  Instead of serving one model at a time, put all 3 of a node's models on its 8
  GPUs at the same time, and work through the tasks one by one: pull the image,
  run all 3 models on it, delete the image. This means:
  - Each 9 GB SEC-bench Pro image is pulled once per node instead of 3 times.
    The local disk (~860 GB on the login node; I haven't checked the compute
    nodes) can't hold all 1.65 TB.
  - All models see exactly the same tasks under the same conditions.
  - CPUs, which are the real bottleneck because of fuzzer runs and V8 rebuilds,
    are shared evenly.
